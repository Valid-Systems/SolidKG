Seven-arm OpenCode benchmark results

Matched architecture-explanation sessions across baseline OpenCode, SolidKG core, SolidKG + SCIP, CodeGraph, Sverklo, Cartog, and Tilth.

10 repositories · 7 arms · 4 repeats per repository-arm cell · 276 completed answers

What the results say

  • Baseline had the fastest observed end-to-end sessions, at 57.9 mean seconds.
  • SolidKG core and SolidKG + SCIP used about 70–71% fewer paired tool calls than baseline.
  • SolidKG core had the lowest mean token usage and lowest estimated GPT-5.6 Sol API-equivalent cost.
  • Mechanism F1 was near-identical across arms, from 97.09% to 98.12%.
  • Sverklo and Cartog had the fastest direct MCP calls, but slower complete sessions and higher estimated API costs than baseline.

API-equivalent pricing methodology

Estimates use GPT-5.6 Sol Standard short-context rates checked 2026-07-12: $5.00/M non-cached input, $0.50/M cached input, $6.25/M cache writes, and $30.00/M output. Reasoning tokens use the output rate.

Formula: (non-cached input × $5.00/M) + (cached input × $0.50/M) + (cache writes × $6.25/M) + (output + reasoning × $30.00/M). These are API-equivalent estimates from raw token usage; actual OpenCode subscription billing recorded $0.

Availability and parser-tier notes

CodeGraph completed 36 of 40 cells because four .NET Runtime indexing cells were terminal unavailable in this frozen setup. This is an availability observation for this setup, not a general C# support claim.

Sverklo was available for all 40 cells. Its documented support includes tree-sitter-capable TypeScript/TSX, JavaScript, Python, Go, Rust, and C#, plus regex fallback for PHP, Java, Ruby, and other registered languages. The benchmark did not prove which parser handled each runtime cell.

Statistical note

For the SolidKG tool-call reductions, the raw exact sign-flip p-value was .00195. The predeclared Holm-adjusted p-value across the comparison-endpoint family was .140625. Treat the reductions as descriptive effects, not multiplicity-adjusted statistical findings.

Study design and limits

Ten repository-specific architecture questions were run across seven arms with four repeats per repository-arm cell. Two blinded SOL-high reviewers scored every completed answer, with a separate adjudication session for scored-field disagreements.

The benchmark covers architecture explanations, not generated patches, build success, regressions, security, maintenance work, or human productivity. One model, one host, four repeats per cell, and ceiling-limited quality constrain generalization. Direct latency used four process-level repeats; indexing preparation time was excluded.
